# TermOne 竞品分析与需求规划

> 形态说明：本文件为「产品策略分析 + 需求梳理」产物（精简版）。依据现有代码盘点、竞品公开资料、以及项目原始需求（`docs/需求.md` + `README.md`）综合分析，提出新需求与优化项，并按 MoSCoW 给出优先级与版本路线。凡标注「估算」者均为工程粗估，需排期时二次确认。

## 0. 摘要（Executive Summary）

**TermOne 当前定位**：基于 Tauri 2 + React 的**轻量、漂亮**的跨平台终端（Windows / macOS），参考 Tabby、WindTerm 设计。核心差异点是「本地优先 + 自托管云同步 + 密钥永不上传」。

**关键洞察（竞品反差）**：
- Tabby 官方 README **自承「not lightweight」**（自己都建议内存敏感用户改用 Alacritty/ConEmu）——这正是 TermOne 的护城河。
- WindTerm、Termius 都把 **SFTP 文件管理、分组会话树、端口转发、日志** 当作「基本盘」，而 TermOne 当前均缺失。
- 用户原始需求仅要求「终端 + 跨平台 + 本地 SQLite + 云端同步备份账号信息」，属于**最小可用闭环**；竞品已把门槛拉到「SSH 工作台」级别。

**结论**：在守住「轻量、漂亮、隐私」三条红线前提下，优先补齐 **Must 级体验闭环**（SFTP、分组、分屏、自动重连、同步加密），把重功能（插件市场、AI、移动端）后置。避免在 v0.1 阶段就功能膨胀而丢掉差异化。

## 3. 用户需求与使用场景分析

### 3.1 需求来源与原始诉求
- `docs/需求.md`：「终端软件，需跨平台，参考 Tabby/WindTerm，轻量、漂亮，win+macOS，本地 SQLite + 服务端可同步备份账号信息。」
- 即：原始诉求是**连接管理 + 跨设备配置同步**，不是「AI 终端」或「重型 IDE」。

### 3.2 用户画像（待真实调研确认，当前为假设）
| 画像 | 身份 | 核心目标 | 典型痛点 | 能力水平 |
|---|---|---|---|---|
| P1 全栈/运维 | 管理数台~数十台服务器的开发者 | 快速连服务器、传文件、多开对比 | 换机重配、无图形化传文件 | 熟练 |
| P2 嵌入式 | 调 ESP32/树莓派/路由的硬件党 | 串口调试 + 偶尔传固件 | 工具分散、需 Zmodem | 中等 |
| P3 多设备用户 | Win 办公 + Mac 家里的个人开发者 | 配置/账号在多端一致 | 手动拷配置易丢 | 熟练 |

### 3.3 核心场景（用户旅程）
1. **感知→进入**：打开 TermOne，侧边栏看到分组后的连接档案。
2. **操作**：点档案秒连；需要传文件时右侧开 SFTP 面板拖拽；多机操作时分屏 + 广播。
3. **完成/离开**：长时间任务挂后台有重连保活；关闭时确认防误关（已实现）；配置自动静默同步。
4. **跨设备**：新电脑登录即恢复全部账号信息（已实现同步，但缺分组导致恢复后杂乱）。

### 3.4 成功指标（建议，可衡量）
| 指标 | 口径 | 目标值（建议） |
|---|---|---|
| 首次连接耗时 | 点档案到可输入命令的时长 | < 3s |
| 配置同步成功率 | 双端一致率（LWW 下的同名冲突解决） | ≥ 99% |
| 日活会话数/用户 | 单日打开会话数 | 待基线 |
| 换机恢复时长 | 新设备登录到全部档案可用的时长 | < 1 min |
| 安装包体积 / 内存占用 | 对比 Tabby 同环境 | 维持「轻量」档（估算 ≤ 80MB 安装 / ≤ 120MB RSS） |

### 4.1 重点需求验收标准（Top Must）

**R-01 SFTP 图形化文件管理**
- Given 已建立 SSH 会话，When 用户点击「文件」面板，Then 展示远程家目录树与本地目录树，支持双向拖拽上传/下载。
- Given 传输中，When 网络中断，Then 任务暂停并可重试，不损坏已传文件。
- 非功能：单文件 ≥ 50MB 传输不卡死主终端；不引入 russh 级别的额外原生依赖（优先复用系统 `sftp` 子系统或轻量 SFTP 实现，以守轻量）。

**R-02 连接分组 / 会话树**
- Given 用户有 >10 个档案，When 在侧边栏建分组并拖入，Then 分组折叠/展开持久化并参与云同步。
- Given 搜索框输入关键字，When 查询，Then 跨分组过滤并高亮匹配档案。
- 数据：分组为 `profiles` 表新增 `group` 字段（或独立 `groups` 表），纳入现有 LWW 同步协议。

**R-03 分屏**
- Given 当前有 1 个会话，When 用户触发「右分屏」，Then 新窗格打开空白或指定档案，独立滚动/输入。
- Given 关掉某个分屏，When 操作，Then 其余窗格不受影响，布局可保存。
- 非功能：同时 4 分屏时 RSS 增量 ≤ 估算 60MB。

**R-04 自动重连 + 保活**
- Given SSH 会话因网络抖动断开，When 检测到 EOF，Then 在 N 秒（默认 5s，可配）后自动重连并恢复原 shell 目录（如支持）。
- Given 长连接空闲，When 超过保活阈值，Then 发送 SSH 心跳避免被中间设备掐断。

## 5. 推荐版本路线（MVP → 迭代）

**v0.2（MVP 体验闭环，Must）**：R-02 分组 → R-04 自动重连 → R-03 分屏 → R-01 SFTP。
> 理由：先解决「管理混乱 + 易断 + 多任务 + 传文件」四个最痛点，构成可用 SSH 工作台最小闭环，且不突破轻量红线。

**v0.3（差异化加固，Should）**：R-05 同步 E2EE → R-07 Snippets → R-08 日志 → R-09 历史 → R-06/R-10 转发与跳板 UI。
> 理由：把「隐私 + 效率」卖点做实，转发/跳板补齐运维刚需。

**v0.4+（增值层，Could）**：R-11 主题/插件 → R-13 Quake → R-14 广播 → R-12 AI 辅助（默认关）→ R-15 Zmodem/Sixel → R-16 Linux → R-17 自动化。
> 理由：重功能后置，待轻量定位站稳、用户基数形成后再扩展生态。

**明确不做（Won't）**：R-18 移动端、R-19 重型 IDE。

## 6. 风险登记册

| 编号 | 风险 | 类别 | 概率 | 影响 | 等级 | 应对 |
|---|---|---|---|---|---|---|
| RK-01 | SFTP 走 russh 会引入重原生依赖，破坏「轻量」 | 技术/体验 | 3 | 4 | 12 中 | 优先复用系统 `sftp` 子系统或轻量实现；设内存预算红线 |
| RK-02 | 功能叠加导致安装包/内存膨胀，丢差异化 | 体验/战略 | 4 | 5 | 20 高 | 每版本设「轻量预算」(体积/RSS)，超阈叫停；重功能默认模块懒加载 |
| RK-03 | E2EE 与「服务端搜索/管理」冲突 | 技术 | 3 | 3 | 9 中 | 同步设计为纯客户端加解密，服务端只存密文，不提供服务端检索 |
| RK-04 | 云同步 LWW 在并发编辑同名档案时覆盖用户数据 | 数据 | 2 | 4 | 8 中 | 冲突时保留双副本/提示；关键字段加版本号 |
| RK-05 | 分屏/广播引入并发会话状态错误 | 技术 | 3 | 3 | 9 中 | 会话状态机隔离；单测覆盖多会话生命周期 |
| RK-06 | AI 辅助默认开启触碰隐私/轻量定位 | 合规/体验 | 2 | 4 | 8 中 | 默认关闭、需用户主动填 API Key；不收集终端内容 |
| RK-07 | 自动重连误判导致无限重连刷屏 | 体验 | 2 | 2 | 4 低 | 指数退避 + 最大重试次数 + 手动停止 |

## 7. 结论与下一步建议

1. **守住三条红线**：轻量、漂亮、隐私（密钥永不上传）——这是 TermOne 对 Tabby/WindTerm 的唯一结构性优势。
2. **先补体验闭环再谈生态**：v0.2 把 SFTP/分组/分屏/重连做扎实，比抢做插件/AI 更重要。
3. **把「自托管同步 + E2EE」做成信任卖点**：相比 Termius 的付费云、Tabby 的插件同步，TermOne 的「自己掌控数据 + 端到端加密」是面向隐私敏感用户的有力叙事。
4. **建议下一步**：从 R-02（分组，成本最低、杠杆最高）启动，1–2 周内可上线并立即改善多主机用户的日常体验；同时排 R-01 SFTP 的技术方案验证（系统 sftp 子系统 vs 轻量库）。
