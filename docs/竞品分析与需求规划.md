## 0. 摘要（Executive Summary）

**TermOne 当前定位**：基于 Tauri 2 + React 的**轻量、漂亮**的跨平台终端（Windows / macOS），参考 Tabby、WindTerm 设计。核心差异点是「本地优先 + 自托管云同步 + 密钥永不上传」。

**关键洞察（竞品反差）**：
- Tabby 官方 README **自承「not lightweight」**（自己都建议内存敏感用户改用 Alacritty/ConEmu）——这正是 TermOne 的护城河。
- WindTerm、Termius 都把 **SFTP 文件管理、分组会话树、端口转发、日志** 当作「基本盘」，而 TermOne 当前均缺失。
- 用户原始需求仅要求「终端 + 跨平台 + 本地 SQLite + 云端同步备份账号信息」，属于**最小可用闭环**；竞品已把门槛拉到「SSH 工作台」级别。

**结论**：在守住「轻量、漂亮、隐私」三条红线前提下，优先补齐 **Must 级体验闭环**（SFTP、分组、分屏、自动重连、同步加密），把重功能（插件市场、AI、移动端）后置。避免在 v0.1 阶段就功能膨胀而丢掉差异化。

### 0.1 战略修订（2026-10-23）：主窗口轻量，增值能力全面插件化

> 依据：`docs/需求.md` 新增章节。用户明确要求「主窗口主打轻量实用，SFTP、AI 辅助等**全部**做成插件模式安装」。

**核心决策**：主窗口不再直接承载任何增值功能，改为 **核心 + 插件运行时 + 官方插件** 三层。

- **保留在核心**：终端/SSH/串口会话、多标签与分屏、档案分组与搜索、SQLite + 云同步、密钥环、主题与基础设置、**插件运行时**。
- **全部插件化**：SFTP 文件管理、AI 命令辅助、广播输入、会话日志回放、Snippets、Zmodem/Sixel、Quake 模式、Triggers 自动化、主题市场。
- **插件形态**：**前端插件为主**（JS/TS 包 + 动态 `import()` 懒加载 + 受限 Host API），零新增原生依赖，跨平台免编译即装即用；核心只保留少量涉密/高频后端 IPC 命令（如 SFTP 的 6 个命令），插件只写 UI 与交互——**插件迭代无需重编 Rust**。
- **对竞品的反超点**：Tabby 自承「not lightweight」，部分能力靠第三方插件拼装；TermOne 走「核心极轻 + 官方插件按需装」，既守住轻量，又不牺牲能力上限。

**优先级影响**：新增 **R-20 插件运行时与插件管理（Must）**，并**前置到 v0.2 首位**（它是所有插件化交付的地基）；R-01 SFTP 改为「以官方插件形态交付」。详细规格见 `docs/插件系统设计.md`。

## 3. 用户需求与使用场景分析

### 3.1 需求来源与原始诉求
- `docs/需求.md`：「终端软件，需跨平台，参考 Tabby/WindTerm，轻量、漂亮，win+macOS，本地 SQLite + 服务端可同步备份账号信息。」
- 即：原始诉求是**连接管理 + 跨设备配置同步**，不是「AI 终端」或「重型 IDE」。

### 3.2 用户画像（待真实调研确认，当前为假设）
| 画像 | 身份 | 核心目标 | 典型痛点 | 能力水平 |
|---|---|---|---|---|
| P1 全栈/运维 | 管理数台~数十台服务器的开发者 | 快速连服务器、传文件、多开对比 | 换机重配、无图形化传文件 | 熟练 |
| P2 嵌入式 | 调 ESP32/树莓派/路由的硬件党 | 串口调试 + 偶尔传固件 | 工具分散、需 Zmodem | 中等 |
| P3 多设备用户 | Win 办公 + Mac 家里的个人开发者 | 配置/账号在多端一致 | 手动拷配置易丢 | 熟练 |

### 3.3 核心场景（用户旅程）
1. **感知→进入**：打开 TermOne，侧边栏看到分组后的连接档案。
2. **操作**：点档案秒连；需要传文件时右侧开 SFTP 面板拖拽；多机操作时分屏 + 广播。
3. **完成/离开**：长时间任务挂后台有重连保活；关闭时确认防误关（已实现）；配置自动静默同步。
4. **跨设备**：新电脑登录即恢复全部账号信息（已实现同步，但缺分组导致恢复后杂乱）。

### 3.4 成功指标（建议，可衡量）
| 指标 | 口径 | 目标值（建议） |
|---|---|---|
| 首次连接耗时 | 点档案到可输入命令的时长 | < 3s |
| 配置同步成功率 | 双端一致率（LWW 下的同名冲突解决） | ≥ 99% |
| 日活会话数/用户 | 单日打开会话数 | 待基线 |
| 换机恢复时长 | 新设备登录到全部档案可用的时长 | < 1 min |
| 安装包体积 / 内存占用 | 对比 Tabby 同环境 | 维持「轻量」档（估算 ≤ 80MB 安装 / ≤ 120MB RSS） |

### 4.0b R-21 Web 版 SSH 验收标准

**范围**：仅远程 SSH，不含本地终端 / 串口 / SFTP / 多标签。

- Given 用户已登录，When 打开 Web 控制台，Then 看到已保存主机列表，点击即建立 SSH 会话并进入可交互终端。
- Given 未携带或携带无效 JWT，When 发起 WebSocket 连接，Then 服务端以 `4401` 关闭，不建立任何 SSH 连接。
- Given 用户新增主机**不勾选**「保存到服务端」，When 保存，Then 主机创建成功且 `hasCredential=false`，数据库与响应中**均无凭据**。
- Given 服务端不持有凭据的主机，When 客户端点击连接且未提供凭据，Then 收到 `该主机未保存凭据，请在客户端输入密码后连接`，前端弹出凭据输入框。
- Given 用户在连接时临时提供凭据，When 连接，Then SSH 正常发起；连接结束后数据库文件仍**不含该凭据明文**（不落盘）。
- Given 用户勾选「保存到服务端」并填写凭据，When 保存，Then 凭据以 AES-256-GCM 加密落盘；随后 `GET /api/ssh/hosts` 的响应与数据库文件中**均不出现凭据明文**。
- Given 用户取消勾选「保存到服务端」，When 保存，Then 服务端凭据被立即删除（`hasCredential=false`）。
- Given 用户编辑主机时凭据留空，When 保存，Then 主机信息更新而原有凭据保持不变。
- Given 用户使用「临时连接」，When 连接，Then 两端都不保存凭据，连接结束后内存中凭据即销毁。
- Given 目标主机公钥指纹与首次连接记录不一致，When 连接，Then 服务端**拒绝连接**并提示疑似中间人攻击。
- Given 终端窗口尺寸变化，When 调整浏览器窗口，Then 远端 PTY 的 `cols/rows` 同步更新。
- Given 桌面端已同步一台 SSH 主机（`/api/sync/push`，kind='profile'），When Web 端打开主机列表，Then **立即可见**该主机（同一 `user_items` 存储，共用主机库）。
- Given 用户在 Web 端新增 / 删除主机，When 桌面端执行同步（pull），Then 该主机出现在本地档案中；删除以 tombstone（`deleted=true`）同步，本地档案同步移除。
- Given 桌面端开启了 E2EE 同步，When Web 端打开主机列表，Then 加密主机被标记为「E2EE」：不可查看详情、不可连接、不可编辑（403），仅可删除（tombstone 不回显内容）。
- Given 桌面端某主机使用 agent 认证，When Web 端连接，Then 提示服务端不持有凭据，需客户端临时提供密码或私钥。

### 4.1 重点需求验收标准（Top Must）

**R-20 插件运行时 + 插件管理**（新增，地基）
- Given 用户未安装任何插件，When 启动应用，Then 冷启动耗时与常驻内存相较无插件版本差异 ≤ 5%，且主 bundle 不含任何插件代码。
- Given 用户从插件管理安装官方 SFTP 插件，When 启用并打开面板，Then 面板正常渲染；未启用时 UI 中不出现任何 SFTP 入口。
- Given 插件渲染时抛异常，When 触发错误边界，Then 显示「插件出错」占位，主窗口与其他插件正常、会话不中断。
- Given 插件调用 manifest 未声明的 IPC 命令，When 执行，Then 立即抛权限错误并记一条审计日志。
- Given 停用/卸载插件，When 操作完成，Then 面板、命令、快捷键、设置项、事件订阅、定时器全部注销，无残留。
- 非功能：插件**零新增原生依赖**，跨平台免编译分发；插件迭代不触发 Rust 重新编译。

**R-01 SFTP 图形化文件管理**（**以官方插件形态交付**）
- Given 已建立 SSH 会话且已启用 SFTP 插件，When 用户点击「文件」面板，Then 展示远程家目录树与本地目录树，支持双向拖拽上传/下载。
- Given 传输中，When 网络中断，Then 任务暂停并可重试，不损坏已传文件。
- Given 未启用 SFTP 插件，When 打开主窗口，Then 无任何 SFTP 相关入口与开销（代码在独立 chunk，未加载）。
- 非功能：单文件 ≥ 50MB 传输不卡死主终端；不引入 russh 级别的额外原生依赖（后端复用系统 `sftp` 子系统，保留在核心）。

**R-02 连接分组 / 会话树**
- Given 用户有 >10 个档案，When 在侧边栏建分组并拖入，Then 分组折叠/展开持久化并参与云同步。
- Given 搜索框输入关键字，When 查询，Then 跨分组过滤并高亮匹配档案。
- 数据：分组为 `profiles` 表新增 `group` 字段（或独立 `groups` 表），纳入现有 LWW 同步协议。

**R-03 分屏**
- Given 当前有 1 个会话，When 用户触发「右分屏」，Then 新窗格打开空白或指定档案，独立滚动/输入。
- Given 关掉某个分屏，When 操作，Then 其余窗格不受影响，布局可保存。
- 非功能：同时 4 分屏时 RSS 增量 ≤ 估算 60MB。

**R-04 自动重连 + 保活**
- Given SSH 会话因网络抖动断开，When 检测到 EOF，Then 在 N 秒（默认 5s，可配）后自动重连并恢复原 shell 目录（如支持）。
- Given 长连接空闲，When 超过保活阈值，Then 发送 SSH 心跳避免被中间设备掐断。

## 5. 推荐版本路线（MVP → 迭代）

> 修订（2026-10-23）：插件运行时 **R-20 前置为 v0.2 第一项**，因为 SFTP 已改为插件形态交付，没有运行时就没有交付载体。

**v0.2（插件化地基 + 体验闭环）**：**R-20 插件运行时** → R-02 分组 → R-04 自动重连 → R-03 分屏 → **R-01 SFTP（作为首个官方插件交付）**。
> 理由：运行时先行，随后解决「管理混乱 + 易断 + 多任务 + 传文件」四个最痛点。SFTP 以插件形态落地，既补齐能力又不牺牲主窗口轻量。

**v0.3（差异化加固 + 插件生态）**：R-05 同步 E2EE → R-07 Snippets（插件化）→ R-08 日志（回放插件化）→ R-09 历史 → R-06/R-10 转发与跳板 UI → **插件市场与 `.tpk` 分发**。
> 理由：把「隐私 + 效率」卖点做实，转发/跳板补齐运维刚需；同时让插件可被安装、更新、分发。

**v0.4+（增值层，全部为插件）**：R-13 Quake → R-14 广播 → R-12 AI 辅助（默认关）→ R-15 Zmodem/Sixel → R-11 主题市场 → R-17 自动化 → R-16 Linux。
> 理由：增值层一律外置为插件，主窗口体积与内存不随功能增长而膨胀。

**明确不做（Won't）**：R-18 移动端、R-19 重型 IDE。

## 7. 结论与下一步建议

1. **守住三条红线**：轻量、漂亮、隐私（密钥永不上传）——这是 TermOne 对 Tabby/WindTerm 的唯一结构性优势。
2. **先补体验闭环再谈生态**：v0.2 把 SFTP/分组/分屏/重连做扎实，比抢做 AI/市场更重要。
3. **把「自托管同步 + E2EE」做成信任卖点**：相比 Termius 的付费云、Tabby 的插件同步，TermOne 的「自己掌控数据 + 端到端加密」是面向隐私敏感用户的有力叙事。
4. **（2026-10-23 修订）插件化是守住轻量的结构性手段，而非功能延后**：
   主窗口只保留「连得上、敲得顺、看得清」，SFTP、AI 辅助等增值能力全部外置为官方插件按需安装。
   这既回应了「轻量实用」的原始诉求，也让功能增长不再与体积/内存线性绑定——
   **Tabby 自承「not lightweight」，而 TermOne 可以做到「功能不比它少，主窗口比它轻」**。
5. **当前交付**（2026-10-24）：运行时、SFTP 插件化与其余增值插件已接入；后续重点为零插件性能量测、Windows/多种 Linux 桌面实机验收、真实 AI 服务及设备互通验证。具体完成状态见覆盖矩阵。
